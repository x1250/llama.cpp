# Resource safety on the Strix Halo desktop (mandatory)

- Before ANY model load or GPU-heavy run: compute the footprint (weights + KV + compute buffers) and require `MemAvailable - footprint >= 40 GiB`. Abort otherwise.
- One load at a time: `pgrep llama-` must be empty before starting; monitor MemAvailable while it runs.
- qwen4exp: lazy mode (`-lzm auto`, 66 GiB) is the only safe config with the desktop up. `-lzm off` / `LAZY=0` pins 93 GiB, leaves ~15 GiB and froze the machine (2026-09-02, freeze #7). Do not run it unless the Director closes the desktop apps first.
- Benchmarks: put every test of one config in ONE llama-bench invocation (one load); separate loads only for env knobs.
- After a process exits, its GTT pages come back to `MemAvailable` asynchronously: the gate must wait (bounded) for the margin, not assume it. A run with host-visible (write-combined) Vulkan memory (`GGML_VK_PREFER_HOST_MEMORY=1`) leaves its pages (~66 GiB) parked in the kernel TTM page pool, outside `MemAvailable`, until memory pressure; `sysctl -w vm.drop_caches=3` (run by the Director, never a privilege dialog from here) releases them. Avoid that env on this desktop.
- A loaded server excludes everything else. No build, bench, perplexity, test or script with a memory footprint may run while any `llama-*` process is alive: `strix unload` first, `pgrep -x "llama-(server|bench|cli|perplexit)"` must be empty, reload production afterwards. Freeze #8 (2026-09-02 20:19): production loaded (lazy qwen4exp + MTP draft, ctx 131072 x 2 slots, ~30 GiB MemAvailable) plus `make -j24` (241 objects in 47 s) froze the machine; hard reset. No kernel message survived, the ram-guard (8 GB, 1 s poll) never fired.
- Builds count as loads: use `strix-halo/build-llama.sh` (refuses to start with a llama process alive, kills the build if MemAvailable drops under its floor). `MemAvailable` is not usable headroom while a model is loaded: it counts the model's hot page cache (the lazy PLE table, up to 27 GiB of mmap), and a burst of anonymous allocations (16-24 compilers) exhausts the real free memory in seconds, faster than the guard's poll. The guard is a last resort, never a budget.
- Production is the model's native context, never less: qwen38flash runs at 262144 x 2 slots (the Director's standing order; 922ab1a lowered it "for memory" without authorization and was reverted). With MTP n-max 2 it leaves ~22 GiB fresh (MemFree ~1 GiB). That margin is for the desktop, not for me: production runs alone, and my tests run only with production unloaded, under the 40 GiB gate, with the test's own context reduced, never production's.
- After a hard reset, do not trust `build/`: products written in the last ~30 s before the freeze can be truncated (freeze #8 left 23 zero-size files, `llama-server` among them) while make considers them up to date, and cmake's generated `.make`/`.cmake` files can be truncated too. Delete the products newer than the last commit (`find build -type f -newermt <ISO time> \( -name '*.o' -o -name '*.so*' -o -name '*.a' -o -path 'build/bin/*' \) -delete`), re-run `cmake -S . -B build`, rebuild, verify `readelf -h` and `--version` before installing.
- Freeze #9 (2026-09-03 03:07): the machine locked up in the middle of a model load (NP=1, ctx 57344, nothing else running, MemAvailable 46 GiB) because MemFree hit 0: the loader read the whole 93 GiB file ahead into the page cache while the GPU pinned 70-85 GiB, and every load did that (MemAvailable never showed it). Fixed in the loader (a7b9fa7ec: bounded read-ahead window, uploaded tensors dropped from the page cache). Rules: during any load MemFree must stay above 4 GiB (a load that drives it under is aborted, it is the freeze signature); the load itself is the risky phase, not only the margin after it; the rigs sample MemFree, not only MemAvailable.
- Freeze #10 (2026-09-16 12:53): a model load right after a large write. A chain quantized a new GGUF (83.5 GiB written in 146 s, mostly verbatim copies) and 12 s later ran `llama-perplexity` on it with `-ngl 99`: the fresh file's pages were still DIRTY in the page cache, and the loader's page-cache drop (a7b9fa7ec) cannot evict dirty pages, so tens of GB of unflushed output stayed resident while the GPU pinned ~57 GiB; MemFree hit 0 and the desktop locked up with no kernel message (hard reset; the new file came back with zeroed tails and was discarded, the source shards were re-verified by sha256). Rules: after writing any large file, `sync` and wait until `Dirty` in /proc/meminfo drains, then drop the page cache of every model file involved (`posix_fadvise DONTNEED`), before any load; every load I launch (perplexity, bench, rig, server) runs under a MemFree kill switch (< 6 GiB -> kill) and the gate checks MemFree >= footprint, not only MemAvailable, which counts dirty pages as available. A quantize is not a load, but what follows it is.
- The session harness kills my background commands when the machine's free memory drops (2026-09-16 20:01 and 20:06): a production reload (MemAvailable 40 GiB, MemFree ~1 GiB, the normal shape of every load) and a GGUF transform through numpy memmaps (the process reached 52 GB of file-backed RSS) both got their chains killed, the first one taking the half-loaded server with it. Rules: every production reload from a chain runs detached (`setsid -f bash -c "./strix load ..."` then poll `/health`), never as a child of the chain; large file transforms copy data inside the kernel (`os.copy_file_range`) and drop both files from the page cache every few GiB (`posix_fadvise DONTNEED`) so MemFree stays high and the process stays small (`scripts/qwen4exp-merge-hc-inject.py`); never edit a chain script while it runs (bash reads it by offset); stop a chain by PID (`kill $(pgrep -f "bash ./$NAME")` with the script name only in a variable, and NOTHING else in that command: no relaunch line, no literal name in any argument): the pattern matches my own shell's command line and the kill takes my shell first (2026-09-18 twice, 2026-09-22 twice; the relaunch goes in a separate command).
- No privilege dialogs from this session: a `pkexec` prompt I launched could not be closed or cancelled and wedged the Director's desktop (2026-09-03). Kernel/sysctl changes are proposed in text for the Director to run; never launched from here.

The fork removed that block (AUTO stays lazy for the marked tensors > 4 GiB on every device): check that it does not come back with each merge. Upstream 992cb503c also dropped the scheduler's split-on-inputs rule and the fork keeps it (commit "ggml: keep the scheduler's split-on-inputs rule"): without it this graph's Vulkan compute buffer grows with the context (3.9 -> 11 GiB at n_ctx 135168). After each merge, probe a load at n_ctx 135168 with the production arguments (NP=1, MTP on, `-lv 4` shows the buffer sizes): Vulkan0 compute buffer ~3.9 GiB, footprint ~79 GiB, and MemAvailable ~26 GiB with production loaded, before installing.
- Upstream PRs #28118 (speculative checkpoints on device) and #28244 (attend only the QSA-selected cells) are fetched as refs/pr/28118 and refs/pr/28244 and apply clean, but they are NOT on master: they enter only after a measured window (decode at 40-64k depth, production unloaded).
- Upstream review of 2026-09-17 (`docs/strix-halo/upstream-review-2026-09-17.md`): the next merge takes `b0dcb8192` first (the server passes the token count as the draft's position; after an image the MTP draft is hundreds of positions off), keeps the fork's sparse FA over upstream's `fc82583e6` (decode-only, f16-only, mask re-scan), keeps the fork's `build_hc_mix` over `37b53fd45` (upstream's hc ops are rejected on Vulkan), and treats `91f6a6cf3` (A-type as a spec constant) as a dedicated window, not a merge resolution. `14a9d09f7` deletes `--mmap/--mlock/--dio`: the launcher already uses `-lm mmap`.
- Never edit sources while a build is running: make picks up the edit mid-build and the binary silently differs from what the bench labels say (2026-09-02: an unplanned graph edit entered a build and produced two hours of contradictory MMQ measurements). Rebuild, then edit.
- Identical requests must give identical logits, and the check is part of every backend change: `repeat_probe.py <tag> 5 0 0` against production (five full prefills of the 4.7k-token agent prompt, `cache_prompt: false`, same top-4 probabilities every time) and `graph_diff4` with `GD_MODES=seq_rm GD_SPLIT=2048,631` (the server's checkpoint split; tools in `~/dbg/merge`). Since the SET_ROWS merge the tool reports 72 differing nodes on every build, the base included: the whole-cache views of the 12 QSA layers' `cache_idx_k`/`cache_k`/`cache_v` SET_ROWS nodes in both ubatches, read at node time before the second ubatch's rows are written (zeros in run 1, stale data in run 2). The gate is: only those 72 differ, every other node identical (2026-09-22); the tool still has to compare only the written rows. Two Vulkan defects broke it (found 2026-09-09, both in the shaders): the radix top-k emitted its ties in scheduling order, and QSA scores tie across every block of 4 cells; and the coopmat1 flash attention let the V of a masked cell move the last row of a tile by one f16 ulp (a zero weight times a negative value), so the free cells past the end of a sequence, which keep a previous request's data inside the 256-cell window, changed the last token of every partial ubatch. Each request then re-read the previous request's garbage and the first-token probability drifted 75.8 -> 30.4 -> 55.3 -> 33.7 % over identical requests; at the agent level this was "the user asks in Chinese" / "the user has not asked anything". A fresh cache (zeros) hides both: test after a previous request, never only on a fresh load. The 4.7k probe runs below the sparse threshold (16.4k cells): every change to the sparse paths is also checked at depth with `depth_repeat.py` after the 40k depth rig (`mtp_depth.sh <tag> 1 2` with `DEPTH_EXTRA=depth_repeat.py`): the same question five times on the cached prefix, the small-batch runs 2 and 3 and the batched re-prefill runs 1 and 5 identical in tokens and first-token logprobs. A third defect lived there (found 2026-09-09): the decode-mode list prepass appended its chunks through an atomic, so the list order, and the attention's rounding with it, followed the GPU's scheduling; identical requests at 40k differed by 0.05 in the first logprob and diverged after 210 characters. Fixed with a two-pass, fixed-order prepass (38462e9a2).
- Every measurement chain re-runs the baseline config in the same chain (first and last); the Vulkan graph optimizer's concurrency makes results sensitive to graph node order, so a source change outside the backend can move numbers by 10%.
- GPU job timeout: kernel 7.0 defaults `amdgpu.lockup_timeout` to 2000 ms on every ring (it was 10 s gfx / 60 s compute). Any single Vulkan submission longer than 2 s resets the compute queue and llama-server dies with `ErrorDeviceLost` (2026-09-03 21:22: slot 1 at 121k, a 2048-token re-prefill; journal: `ring comp_1.3.1 timeout ... Process llama-server`; the desktop survives, it is a per-queue reset). Every attention prefill of qwen4exp, the QSA layers and the dense MTP draft block alike, is split into query blocks bounded by work (`qsa_query_block`: 2048 x 32768 query-cells per block, so nothing changes below 32k of context) and no submission grows with depth: 126.5k-token prefill 524 s and 2048-token re-prefill at 126k 12 s without a reset. The first fix covered only the QSA layers and production died again at 128k on the draft's dense attention (2026-09-04 01:14): a depth test must run with the production feature set (MTP on). The production feature set also includes vision (the mmproj is loaded): image cells share one mrope position, which switches the QSA block grouping from position to rank order, and the pooled-summary tables sized by position asserted on the first short text ubatch after an image (2026-09-04 02:0x, `n_dirty < n_dirty_max`). Any change to the QSA cache paths is tested with a text -> image -> short text conversation. Every new depth-dependent node must respect that budget. The vision encoder runs on the GPU since 2026-09-22 (launcher `MMPROJ_OFFLOAD=1`; on the CPU it took 30 s for a 448x448 image and 381 s at the cap): the largest image the Qwen3-VL projector accepts (2048x2048, 4096 tokens, 16384 patches) encodes and prefills in 14.6 s with no ring timeout, and any change to the vision path re-runs that image (`img_big.py <tag> 2048 2048`) besides the conversation. `test-backend-ops perf -o FLASH_ATTN_EXT` over the whole suite is not safe here: the upstream MLA case (hsk=576, hsv=512, kv=32768, nb=1) is one submission longer than 2 s and reset the compute queue with `ErrorDeviceLost` in all three runs of 2026-09-22 (15:46, 16:20, 16:53; the qwen4exp cases had already run); filter the perf run to the qwen4exp shapes. `amdgpu.lockup_timeout=10000` in GRUB restores the historical margin; the Director decides and runs it.
