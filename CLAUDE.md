# Resource safety on the Strix Halo desktop (mandatory)

- Before ANY model load or GPU-heavy run: compute the footprint (weights + KV + compute buffers) and require `MemAvailable - footprint >= 40 GiB`. Abort otherwise.
- One load at a time: `pgrep llama-` must be empty before starting; monitor MemAvailable while it runs.
- qwen4exp: lazy mode (`-lzm auto`, 66 GiB) is the only safe config with the desktop up. `-lzm off` / `LAZY=0` pins 93 GiB, leaves ~15 GiB and froze the machine (2026-09-02, freeze #7). Do not run it unless the Director closes the desktop apps first.
- Benchmarks: put every test of one config in ONE llama-bench invocation (one load); separate loads only for env knobs.
- After a process exits, its GTT pages come back to `MemAvailable` asynchronously: the gate must wait (bounded) for the margin, not assume it. A run with host-visible (write-combined) Vulkan memory (`GGML_VK_PREFER_HOST_MEMORY=1`) leaves its pages (~66 GiB) parked in the kernel TTM page pool, outside `MemAvailable`, until memory pressure; `sysctl -w vm.drop_caches=3` (run by the Director, never a privilege dialog from here) releases them. Avoid that env on this desktop.
- A loaded server excludes everything else. No build, bench, perplexity, test or script with a memory footprint may run while any `llama-*` process is alive: `strix unload` first, `pgrep -x "llama-(server|bench|cli|perplexit)"` must be empty, reload production afterwards. Freeze #8 (2026-09-02 20:19): production loaded (lazy qwen4exp + MTP draft, ctx 131072 x 2 slots, ~30 GiB MemAvailable) plus `make -j24` (241 objects in 47 s) froze the machine; hard reset. No kernel message survived, the ram-guard (8 GB, 1 s poll) never fired.
- Builds count as loads: use `strix-halo/build-llama.sh` (refuses to start with a llama process alive, kills the build if MemAvailable drops under its floor). `MemAvailable` is not usable headroom while a model is loaded: it counts the model's hot page cache (the lazy PLE table, up to 27 GiB of mmap), and a burst of anonymous allocations (16-24 compilers) exhausts the real free memory in seconds, faster than the guard's poll. The guard is a last resort, never a budget.
- Production is the model's native context, never less: qwen38flash runs at 262144 x 2 slots (the Director's standing order; 922ab1a lowered it "for memory" without authorization and was reverted). With MTP n-max 2 it leaves ~22 GiB fresh (MemFree ~1 GiB). That margin is for the desktop, not for me: production runs alone, and my tests run only with production unloaded, under the 40 GiB gate, with the test's own context reduced, never production's.
- After a hard reset, do not trust `build/`: products written in the last ~30 s before the freeze can be truncated (freeze #8 left 23 zero-size files, `llama-server` among them) while make considers them up to date, and cmake's generated `.make`/`.cmake` files can be truncated too. Delete the products newer than the last commit (`find build -type f -newermt <ISO time> \( -name '*.o' -o -name '*.so*' -o -name '*.a' -o -path 'build/bin/*' \) -delete`), re-run `cmake -S . -B build`, rebuild, verify `readelf -h` and `--version` before installing.
- Freeze #9 (2026-09-03 03:07): the machine locked up in the middle of a model load (NP=1, ctx 57344, nothing else running, MemAvailable 46 GiB) because MemFree hit 0: the loader read the whole 93 GiB file ahead into the page cache while the GPU pinned 70-85 GiB, and every load did that (MemAvailable never showed it). Fixed in the loader (a7b9fa7ec: bounded read-ahead window, uploaded tensors dropped from the page cache). Rules: during any load MemFree must stay above 4 GiB (a load that drives it under is aborted, it is the freeze signature); the load itself is the risky phase, not only the margin after it; the rigs sample MemFree, not only MemAvailable.
- No privilege dialogs from this session: a `pkexec` prompt I launched could not be closed or cancelled and wedged the Director's desktop (2026-09-03). Kernel/sysctl changes are proposed in text for the Director to run; never launched from here.
- Upstream PRs #28118 (speculative checkpoints on device) and #28244 (attend only the QSA-selected cells) are fetched as refs/pr/28118 and refs/pr/28244 and apply clean, but they are NOT on master: they enter only after a measured window (decode at 40-64k depth, production unloaded).
- Never edit sources while a build is running: make picks up the edit mid-build and the binary silently differs from what the bench labels say (2026-09-02: an unplanned graph edit entered a build and produced two hours of contradictory MMQ measurements). Rebuild, then edit.
- Every measurement chain re-runs the baseline config in the same chain (first and last); the Vulkan graph optimizer's concurrency makes results sensitive to graph node order, so a source change outside the backend can move numbers by 10%.
- GPU job timeout: kernel 7.0 defaults `amdgpu.lockup_timeout` to 2000 ms on every ring (it was 10 s gfx / 60 s compute). Any single Vulkan submission longer than 2 s resets the compute queue and llama-server dies with `ErrorDeviceLost` (2026-09-03 21:22: slot 1 at 121k, a 2048-token re-prefill; journal: `ring comp_1.3.1 timeout ... Process llama-server`; the desktop survives, it is a per-queue reset). Every attention prefill of qwen4exp, the QSA layers and the dense MTP draft block alike, is split into query blocks bounded by work (`qsa_query_block`: 2048 x 32768 query-cells per block, so nothing changes below 32k of context) and no submission grows with depth: 126.5k-token prefill 524 s and 2048-token re-prefill at 126k 12 s without a reset. The first fix covered only the QSA layers and production died again at 128k on the draft's dense attention (2026-09-04 01:14): a depth test must run with the production feature set (MTP on). Every new depth-dependent node must respect that budget. `amdgpu.lockup_timeout=10000` in GRUB restores the historical margin; the Director decides and runs it.
